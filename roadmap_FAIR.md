# FAIR metadata for DOME Observatory: Dublin Core, DCAT, schema.org, JSON-LD and OAI-PMH

## Context

`ROADMAP.md` items 6 (DCAT) and 7 (schema.org / JSON-LD) are one line each, with a notes line asking
about Dublin Core, JSON-LD and OAI-PMH. The Observatory's integrations page
(`dome-ml-observatory/observatory-ui/src/app/about/about-integrations/about-integrations.ts`)
already lists OAI-PMH as planned. The aim is a more FAIR resource (Wilkinson et al. 2016). You asked
four things: which standard to use, whether to change the schema or moros, where each piece is built
and served, and what OAI-PMH needs.

Facts this report rests on, checked in both repositories and online:

- **Documents.** moros holds plain JSON on MongoDB 4.2: 846,716 documents at schema 1.4.0, with
  `_id` a UUID5 minted by `mongo_landscape_export/scripts/pid.py`.
- **Service.** `observatory-ws` (NestJS) is the only reader. `observatory-ui` is a static Angular
  SPA with no SSR, served by nginx (`try_files … /index.html`). The record page sets no `<title>`,
  meta tags or JSON-LD.
- **Vocabularies.** The vocabulary files already carry IRIs: `domain_vocab.json` has `edam_id` and
  `modelling_branch_vocab.json` has `mesh_id`. The documents do not store IRIs, and the
  `mesh_headings` entries are labels with no descriptor ids.
- **No record-level modified date.** Only per-group timestamps exist (`llm_classification.timestamp`,
  `citation_count_updated`, `data_links.fetched_at`, `llm_enrichment.timestamp`).
- **Licences are split.** CC BY 4.0 covers only the layer this project adds. Abstracts and
  bibliographic metadata keep Europe PMC's terms (`dome-ml-observatory/LICENSE.md`).
- **The dataset DOI is dead.** The Zenodo DOI on `/download/bulk` is not registered (observatory
  roadmap item 4). The archive job that would mint a real one is triage roadmap item 5.
- **DOME family precedent.**
  - The DOME Registry v1 backend already serves schema.org JSON-LD with Bioschemas `conformsTo`
    from NestJS (`dome_registry/dome-registry/dome-registry-ws/src/review/Json-ld/`, routes
    `/markup/dataCatalog`, `/markup/dataset`, `/markup/:shortid`).
  - It also has the identifiers.org prefix `dome`.
  - Registry v2 lists Bioschemas as live and DCAT, Dublin Core and OAI-PMH as planned.
- **External facts (checked online).**
  - Google Dataset Search reads both schema.org `Dataset` and W3C DCAT, and supports structured data
    generated by JavaScript.
  - Bioschemas profiles: Dataset 1.0-RELEASE, DataCatalog 0.3-RELEASE, ScholarlyArticle
    0.3-DRAFT.
  - FAIR Signposting uses typed `Link` headers: `cite-as`, `describedby`, `type`, `license`,
    `item`, `collection`, `linkset`.

## 1. Short answer

1. **Leave moros and the schema alone.** The schema stays the internal, validated, versioned contract.
   Every standard becomes a **read-time projection** in `observatory-ws`, computed from the stored
   document on request. Nothing is stored twice.
2. **The standards are not rivals.** Each describes a different level:
   - **Per record** (a paper plus the Observatory's annotation of it): **schema.org (Bioschemas)
     with Dublin Core terms, in JSON-LD.** DCAT does not fit here.
   - **The corpus as a whole** (the dataset, its monthly releases, the API): **DCAT 3**, mirrored
     as a schema.org `Dataset`. It is generated where a release is made, in triage.
   - **Harvesting:** **OAI-PMH with `oai_dc`** (Dublin Core), served by `observatory-ws`.
3. **Only OAI-PMH needs a database change.** It needs one additive field: a record-level
   last-modified datestamp with an index. Nothing else touches moros.
4. **Order of work:**
   1. Per-record JSON-LD, signposting and a sitemap. This is the largest FAIR gain and needs no
      database change.
   2. Corpus DCAT, built on the Zenodo archive job (roadmap item 5).
   3. OAI-PMH last. It has the lowest real reuse value for a corpus derived from papers that are
      already indexed elsewhere.

## 2. What each standard is, and how it fits

| | What it describes | Fits a record? | Fits the corpus? | Who reads it | Notes |
|---|---|---|---|---|---|
| **Dublin Core Elements 1.1** ("simple DC", `oai_dc`) | Any resource, 15 flat, optional, repeatable text elements | Coarsely: title, creator, date, identifier, subject, description, rights, relation | Weakly | OAI-PMH harvesters (**mandatory** there), library catalogues | Loses what the Observatory adds: the classification, EDAM and MeSH IRIs, and typed data links. `DC.*` HTML meta tags in a JS-rendered SPA have almost no consumers today. |
| **DCMI Terms** (`dcterms`) | ~55 RDF properties with ranges | **Yes**, as properties inside JSON-LD: `dct:title`, `dct:identifier`, `dct:subject` (EDAM IRI), `dct:license`, `dct:references` (data links), `dct:source` | Yes (DCAT reuses it) | Anything that reads RDF | The useful kind of Dublin Core: used inside JSON-LD and DCAT rather than published on its own. |
| **DCAT 3** (W3C Rec, 2024) | Datasets, distributions, data services, catalogues, series | **No.** A record annotates a paper; it is not a dataset. Typing 846k records as `dcat:Dataset` would swamp any catalogue. | **Very well**: DatasetSeries → monthly Dataset → Distributions (Zenodo NDJSON, `/api/export`) + DataService (the API, OpenAPI at `/api/docs-json`) | EOSC / DCAT-AP catalogues, data.europa.eu, FAIR evaluators, Google Dataset Search | Data-link targets can be typed as datasets within a record's graph. |
| **schema.org + Bioschemas** | Things on the web: `ScholarlyArticle`, `Dataset`, `DataCatalog`, `DefinedTerm` | **Yes**: `ScholarlyArticle` plus the annotation | Yes: `Dataset` / `DataCatalog` | Google, Bing, Bioschemas harvesters, FAIR checkers, LLM crawlers | Loose semantics. The ELIXIR community standard, and the DOME Registry already uses it, so the family stays consistent. |
| **JSON-LD** | **Not a vocabulary.** A JSON serialisation of RDF | — | — | — | The container for the three rows above. The real choice is which vocabularies to put inside JSON-LD, at which level. |

### A record is two things, and the output must keep them apart

Each `/record/<pid>` page is about two entities with different licences and provenance:

- **The article**, which is external. Its metadata comes from Europe PMC under its own licence
  (e.g. `"cc by"`, or none).
  - Output node: `@id https://doi.org/…`, type `ScholarlyArticle`, `sameAs` the Europe PMC, PMC
    and PubMed URLs, its own `license`.
- **The Observatory record**, which is the project's contribution: classification, enrichment and
  data links, under CC BY 4.0, generated by the LLM pipeline or a human curator, at a schema version.
  - Output node: `@id https://observatory.dome-ml.org/record/<pid>`, `about` → the article, licence
    CC BY 4.0, `isPartOf` the corpus dataset, `dct:conformsTo` the schema release.
  - Provenance (`prov:wasGeneratedBy`) comes from `model_id`, `prompt_version`, `ruleset_sha256`,
    `batch_id`, `timestamp` and `decision_provenance`.

Merging the two would put CC BY 4.0 on abstracts the project does not own. That contradicts
`LICENSE.md` and fails FAIR R1.1.

### Gaps in the stored data a projection must handle (no schema change needed)

| Field | Stored as | Projection |
|---|---|---|
| `authors` | One string, `"Liang L, Liang H, …"` | Split into `Person` names. Lossy: no ORCIDs, surname and initials only. |
| `year` | An integer | `datePublished: "2025"` |
| `domain_tier*` | Terms | EDAM IRI `http://edamontology.org/topic_XXXX` via the release vocab `edam_id` |
| `learning_paradigm` / `model_family` | Terms | MeSH IRI `http://id.nlm.nih.gov/mesh/<mesh_id>`. The 4 project extensions have `mesh_id: null` and get a project-namespace IRI. |
| `mesh_headings`, `model_type`, `keywords_author` | Labels only | `keywords` as literals. MeSH descriptor IRIs would be a later enrichment. |
| `source.access.license` | `"cc by"`, with no version | An SPDX / Creative Commons IRI map. The version is not asserted when Europe PMC gives none. |
| `abstract`, `title` | Contain HTML | Stripped to plain text. Port `plainText` from `observatory-ui/src/app/core/rich-text.ts`. |
| `data_links.links[]` | `id`, `url` (identifiers.org / doi.org), Scholix `relationship` | Typed references to `Dataset` nodes. Set a partial-list flag when `truncated`. |
| Internal fields (`input_tokens`, `parse_status`, …) | Stored | **Not emitted.** |

## 3. Should moros hold JSON-LD?

**It is possible, but not advisable.** Compact JSON-LD is ordinary JSON, and `@context`, `@id` and
`@type` are legal MongoDB keys. The costs:

- **Every field path changes.** That means rebuilding `positives_text` and `class_year_id` and
  rewriting every `observatory-ws` query, the facet caches, the UI types, `generate_facet_stats.py`,
  the `moros_write.py` `WRITE_MODES` allowlists, the loaders and `check_alignment.py`.
  - All 846,716 documents would need reloading, near the "never drop `Content`" hazard.
  - `AGENTS.md` rule 1 would make it a major versioned change.
- **Expanded JSON-LD uses full IRIs as keys.** Those contain dots, which MongoDB 4.2 cannot address,
  so only the compact form could be stored.
- **Storage would be tied to vocabularies that keep changing** (schema.org releases, DCAT 2 → 3,
  Bioschemas drafts). A mapping tweak would become a data migration.
- **One stored shape cannot serve three outputs.** `oai_dc` XML and DCAT would still need
  projections, so you would pay for the migration and still write the serialisers.
- **Internal operational fields** would either leak into public triples or have to be split out
  anyway.

**Zero-change middle option (optional, cheap):** publish a **JSON-LD context** for the existing API
JSON.

- JSON-LD 1.1 `@nest` treats `identifiers`, `publication_metadata`, `source` and
  `content_filters` as nesting wrappers, so `publication_metadata.title` can map to `dct:title`
  without touching the data.
- Advertise it on `/api/records/:pid` with
  `Link: <…/context/v1.jsonld>; rel="http://www.w3.org/ns/json-ld#context"`. The existing response
  then becomes valid JSON-LD with no change to documents or payload.
- **Trade-off:** the RDF is formally valid but weak. Authors stay one string, terms are not IRIs,
  and article and record are merged.
- **Use:** a cheap I1 layer on the raw API, not a replacement for the curated projection.

**Recommendation: curated projection in `observatory-ws`, and optionally the context on the raw
API. No change to moros or `schema.py` for any of this.**

## 4. Where each piece lives

```
dome-ml-observatory-triage (write side)            dome-ml-observatory (read side)
───────────────────────────────────────            ───────────────────────────────────────────
schema.py ─ authors shape ──────────────────────▶  schema/releases/vX/ (+ vocab edam_id/mesh_id)
                                                        │ baked into the ws image already
[Phase 2] build_release_metadata.py                     ▼
  at Zenodo push (roadmap 5) ─ dataset.jsonld ──▶  metadata/releases/<YYYY-MM>/  ─▶ /api/catalog
                                                   observatory-ws/src/metadata/ (NEW)
[Phase 3] SafeWriter stamps record_modified           record → JSON-LD mapper (pure)
  (+ index, schema 1.5.0) ─────────────────────▶      /api/records/:pid/jsonld, /api/sitemap.xml
                                                   observatory-ws/src/oai/ (Phase 3) ─▶ /api/oai
                                                   observatory-ui: inject JSON-LD on record page
                                                   nginx: signposting Link headers + conneg
```

- **Triage never serves** and **ws never writes**. Both rules hold throughout.
- **The mapper lives in ws, in TypeScript, and is typed and tested.** A Jest test asserts that every
  field path it reads exists in the JSON Schema at `schema/CURRENT` and projects every
  `schema/releases/*/…example.json`.
  - Published and authored schemas are already held equal by `check_alignment.py`, so a triage
    rename breaks that test.
  - No new crosswalk file and no change to the checker.

### The per-record page problem (static SPA)

Every `/record/<pid>` returns the same `index.html` until JavaScript runs.

| Option | Who sees it | Cost | Verdict |
|---|---|---|---|
| a. `record.ts` injects `<script type="application/ld+json">` plus `Title`/`Meta` | Google (renders JS). Not static harvesters or most FAIR checkers. | Small | **Do** |
| b. nginx `location ~ ^/record/([0-9a-f-]{36})$` adds FAIR Signposting `Link` headers (`describedby` → `/api/records/$1/jsonld`, `type`, `license`, `linkset` → ws, which carries `cite-as` = DOI) | Any client, including HEAD requests with no JS. FAIR evaluators. | Small | **Do** |
| c. nginx content negotiation: `Accept: application/ld+json` on `/record/<pid>` proxies to ws, with `Vary: Accept` | Linked-data clients, F-UJI-style checkers | Small to moderate | **Do** |
| d. nginx SSI embeds JSON-LD into `index.html` per request | Static harvesters | Every page view then waits on the API. Caching and CSP care needed. | Only if a static harvester requires it |
| e. Angular SSR / prerender | Everyone | A Node runtime, and 846k prerendered pages is infeasible | No |

**Plus a sitemap.** Record pages sit behind a search form, so crawlers cannot find them without one.
- `GET /api/sitemap.xml`: a sitemap index over `_id` keyset chunks of 50k URLs, reusing the
  `ExportService` cursor.
- Add a `robots.txt`.

**Dublin Core per entry page:** do not add separate `DC.*` meta tags. The same content reaches the
consumers that matter through `dcterms` inside the JSON-LD and through `oai_dc`.

### The corpus (main resource) is generated at triage release time

Only the write side knows the release facts, at the moment it makes a release:
- counts by class (`verify_corpus.py`);
- `SCHEMA_VERSION`;
- criteria and prompt hashes (`prompts/PROMPT_HASHES.json`);
- temporal coverage and the search-space query hashes;
- the refresh date;
- the Zenodo DOI;
- bytes and sha256 per file.

So the dataset description is **built at the triage release point, alongside roadmap item 5**, as
`dataset.jsonld`. It is the planned Zenodo sidecar (count, size, sha256, `schema_version`)
expressed in a standard vocabulary.

- **DCAT 3 structure:**
  - `dcat:DatasetSeries` "DOME Observatory corpus" → a monthly `dcat:Dataset` (`dct:issued`,
    `version`, `dcat:inSeries`).
  - Each monthly dataset → `dcat:Distribution` (Zenodo `.ndjson.gz`, `downloadURL`, `byteSize`,
    `spdx:checksum`, `mediaType`, `dct:conformsTo` schema release URL).
  - `dcat:DataService` for the API (`endpointURL`, `endpointDescription` `/api/docs-json`,
    `servesDataset`).
  - `dct:license` CC BY 4.0 plus a `dct:rights` note on Europe PMC content.
  - `prov:wasGeneratedBy` the pipeline repository and hashes.
- **schema.org `Dataset` / `DataCatalog`** in the same `@graph`, with Bioschemas `conformsTo`,
  matching the Registry's pattern.
- **Publication:** deposited with the Zenodo archive, then published into the observatory repo as
  `metadata/releases/<YYYY-MM>/` + `CURRENT`, the way schema releases are published.
  - ws serves it at `/api/catalog`.
  - The UI injects it on the home page and `/download/bulk`.
  - The same step replaces the dead DOI literal in `download-bulk.ts`.
- **Hard dependency:** without a real Zenodo DOI the corpus has no persistent identifier and still
  fails F1.

## 5. OAI-PMH

- **Format.** OAI-PMH 2.0 makes `oai_dc` **mandatory**, so Dublin Core is the answer here.
  - DCAT and schema.org are not OAI-PMH formats. DCAT catalogues harvest RDF or DCAT-AP endpoints;
    schema.org is found through sitemaps and crawling.
  - Add `oai_openaire` or `oai_datacite` only if OpenAIRE becomes a target.
- **Where it runs.** In `observatory-ws`, as `GET`/`POST /api/oai`, since the protocol requires
  both.
  - It is read-only, which fits both repositories' rules. It is not triage's job.
- **What it needs:**
  - **Identifiers:** `oai:observatory.dome-ml.org:<uuid5>`.
  - **Datestamps (the one schema change in this plan).** `from`/`until` harvesting needs an indexed
    record-level datestamp.
    - Schema **1.5.0** (additive minor): a `record_modified` field (name TBD).
    - `SafeWriter` and `load_documents.py` stamp it.
    - A migrate mode backfills it from the latest of the existing group timestamps.
    - Index `{record_modified: 1, _id: 1}` in `ensure_indexes.py`.
    - Stamp it only in write modes that change fields `oai_dc` exposes. If the monthly `citations`
      refresh bumped it, every harvest would become a full re-harvest.
  - **Resumption tokens:** reuse the export keyset cursor, over `(record_modified, _id)`.
  - **Sets:** e.g. `class:positive`, `domain:<tier1>`.
    - There is no delete path, so `deletedRecord=no` is honest.
    - But a record reclassified out of a set lingers in a set-harvester's copy. Base sets on stable
      properties, or declare `transient`.
  - **Output and limits:** XML validated against the OAI-PMH XSD in tests, and its own throttle
    bucket like `/api/export`.
- **Value, honestly.**
  - The papers are already harvestable from Europe PMC and PMC, and aggregators deduplicate on DOI.
  - What the Observatory adds (classification, EDAM, data links) barely survives 15 flat DC
    elements.
  - OAI-PMH mainly buys FAIR A1 / F4 checkboxes and closes the integrations-page promise. JSON-LD
    and DCAT carry the annotation layer far better. Hence last.

## 6. FAIR (Wilkinson 2016): now and after

| Principle | Today | After | Phase |
|---|---|---|---|
| F1 persistent id | UUID5 is unique and deterministic, but only a URL. Dataset DOI is dead. | Real Zenodo DOI per release; an identifiers.org prefix for records (as the Registry has `dome`) | 2, 4 |
| F2 rich metadata | Rich JSON, no standard vocabulary | schema.org / dcterms projection | 1 |
| F3 metadata names data id | Yes (`_id`, doi) | Explicit `@id`, `cite-as` | 1 |
| F4 indexed | SPA not crawlable, no sitemap | Sitemap, JSON-LD, Google Dataset Search, FAIRsharing / re3data, OAI-PMH | 1–4 |
| A1 open protocol by id | HTTPS API | Plus content negotiation and signposting | 1 |
| A2 metadata outlives data | No | Archived, DOI'd monthly releases with DCAT | 2 |
| I1 formal language | Plain JSON | JSON-LD / RDF | 1 |
| I2 FAIR vocabularies | EDAM and MeSH ids in the vocab files but not in output | Emitted as IRIs | 1 |
| I3 qualified references | DOI/PMID strings, data-link URLs | Typed IRIs (article, datasets, Registry) | 1 |
| R1.1 licence | Prose in `LICENSE.md` | Machine-readable, record vs article split | 1, 2 |
| R1.2 provenance | Rich but unexposed | PROV-O from `llm_classification` | 1 |
| R1.3 community standards | DOME | Bioschemas profile conformance | 1 |

## 7. Implementation plan

**Phase 0: docs, this repo.**
- Done 2026-09-14: this file, linked from `ROADMAP.md`.
- Still to do: the matching item in `dome-ml-observatory/ROADMAP.md`.

**Phase 1: per-record JSON-LD. Observatory repo only, no DB change.**
- **ws module.** New `observatory-ws/src/metadata/` with:
  - `record-jsonld.mapper.ts` (pure);
  - `GET /api/records/:pid/jsonld` and `/api/records/:pid/linkset`;
  - `GET /api/sitemap.xml`;
  - an optional `/api/context/v1.jsonld`.
- **What it reuses:** `RecordsService.findByPid` and the `ExportService` cursor, with the release
  vocab loaded from `schema/releases/<CURRENT>/vocab/`.
- **UI:** `observatory-ui/src/app/record/record.ts` injects the JSON-LD and sets `Title`/`Meta`.
- **nginx:** `observatory-ui/nginx.conf` gets the signposting `Link` headers and content
  negotiation. Check that the CSP still holds, in the container (per `AGENTS.md`).
- **Integrations page:** add schema.org / Bioschemas, DCAT and Dublin Core entries, as Registry v2
  does.

**Phase 2: corpus DCAT. After triage roadmap item 5.**
- **Triage:** `moros_pipeline/scripts/build_release_metadata.py` builds `dataset.jsonld` from the
  corpus verification counts, `SCHEMA_VERSION`, the prompt hashes and the Zenodo response, and
  deposits it with the archive.
- **Observatory:**
  - Add `metadata/releases/` and `/api/catalog`.
  - Inject the dataset JSON-LD on the home page and `/download/bulk`.
  - Fix the DOI literal.
- **Optional:** a DCAT-AP 3 SHACL check.

**Phase 3: OAI-PMH. Both repos, one additive schema bump.**
- **Triage:**
  - Schema 1.5.0 `record_modified`.
  - `WRITE_MODES` entries and a `SafeWriter` stamp.
  - The migrate mode and index.
  - `check_alignment.py`, then publish with the `schema-version` skill.
- **ws:** `src/oai/` with the six verbs, `oai_dc` from the same mapper, cursor resumption tokens,
  its own throttle and XSD-validated tests.

**Phase 4: registrations (no code).**
- Register the database in FAIRsharing and re3data, and an identifiers.org prefix.
- Run F-UJI and FAIR-Checker on a record URL and on the dataset **before Phase 1 and after each
  phase**. That gives a measurable FAIR outcome to report.

## Open decisions for you (they do not block Phase 0 or 1)

1. **Which records get indexed** (sitemap, JSON-LD): positives only (~366k) or all 846k screened?
   Indexing negatives advertises "not AI/ML" pages.
2. **Persistent-identifier route for records:** an identifiers.org prefix, w3id.org, or URLs only.
3. **OAI-PMH:** build it, accepting the one schema bump, or reword the integrations entry.
4. **DCAT publisher / creator** (BioComputingUP, University of Padua, ELIXIR?), and one shared
   DOME-ML catalogue with the Registry or a separate one.
